# 项目定位与目标

> 本文记录当前已经形成共识的项目定位、目标与原则。它用于回答“这个项目为什么存在、要成为什么、服务于怎样的协作方式”，不讨论具体技术实现，也不提前规定项目空间的详细治理制度。

## 1. 背景

随着需求分析、研发、测试等工作逐渐由 Agent 参与或执行，人仍然需要反复为不同 Agent 补充散落在产品文档、设计稿、代码仓库、历史任务和项目成员经验中的项目上下文。

现有协作方式通常将连续性绑定在某个 Agent 或某次团队运行上：

- 在主 Agent—SubAgent 模式中，主 Agent 选择上下文、拆分并派发工作，SubAgent 在独立生命周期内完成任务后返回结果。
- 在由 Leader 组织的 Agent Team 中，成员可以拥有独立上下文并相互协作，但团队的创建、当前局势和延续仍然容易依赖 Leader 或团队实例。
- 当 Agent、会话或团队结束时，许多项目认知、决策依据、工作状态和经验无法自然地被下一位成员继承。

问题的本质不是 Agent 缺少更多材料，而是项目缺少一个独立于任何单一成员、能够长期维护共同认知和协作连续性的载体。

## 2. 对“项目”的定义

本系统以“项目”而不是单个代码仓库、Agent 会话或临时团队作为基本单位。

项目是：

> 围绕一个长期存在的产品、业务领域或软件系统，由多种角色共同维护的一致认知与决策边界。

一个项目可以包含：

- 多个产品端和用户触点；
- 多个代码仓库、服务、模块及其依赖；
- PRD、设计、接口、任务和测试等原始材料；
- 开发、测试、灰度、生产等运行环境；
- 产品、设计、研发、测试、运维等业务与工程角色；
- 长期形成的术语、决策、约束、经验和未解决问题。

项目长期存在；需求、版本、故障和专项是项目内部有开始和结束的工作事项；团队则是项目在某一阶段、围绕某些工作形成的成员组合。

## 3. 核心判断：连续性属于项目

本项目最核心的变化是将连续性的所有权从 Agent 转移给项目：

```text
Agent 中心模式

主 Agent / Leader
    ↓ 创建团队、选择上下文、调度工作
Agent 成员
    ↓ 返回结果
任务或团队结束，连续性依赖原有 Agent 保留
```

```text
项目中心模式

项目长期存在
    ↕
人类与 Agent 加入、协作、退出、替换
    ↕
项目认知、工作状态、决策与责任持续存在
```

Agent 是项目中可进入、可离开、可替换的成员。任何单一 Agent，包括 Leader，都不独占项目上下文，也不构成项目延续的必要条件。

新成员应能从项目恢复必要认知和当前局势后开始工作；成员离开时，已经外化的关键认知、工作责任和决策依据仍然属于项目。

## 4. 项目定位

本项目的定位是：

> 一个依附于项目、面向所有经授权成员、由人类治理、会随项目持续成长的共享认知与协作基座。

进一步说，它是：

> 一个以项目为持续主体的 Agent 原生协作空间。具有独立生命周期的人类与 Agent，以带有角色、责任和权限的项目成员身份加入其中，通过项目共有的认知、工作状态与治理规则协作；成员可以变化，但项目的认知、决策、承诺和工作连续性不会随任何单一成员消失。

这个定位包含三个相互关联但不能混为一谈的层次：

```text
共享认知层       系统内核：维护项目特有、可继承的共同认知
项目协作空间     产品形态：承载成员、工作、责任、决策和交接
项目原生 A2A     协作方式：独立 Agent 作为项目成员共同工作
```

本文所称的 A2A，强调的是独立 Agent 之间以项目为共同依附的协作关系，而不是特指某一种通信协议。通信协议可以承载交互，但不能单独提供项目的组织记忆、成员关系和治理制度。

## 5. 系统形态

系统不是挂在某个仓库上的记忆文件，也不是某个 Agent 的附属工具。它表现为一个独立于当前成员、长期存在的项目空间。

项目空间在概念上承载三类制度性状态：

### 5.1 项目认知

项目是什么、为什么如此、当前相信什么、依据是什么、适用于哪里，以及哪里仍然存在冲突或未知。

项目认知不是原始材料的简单汇总，而是会影响项目行动、无法仅凭当前代码或材料被低成本且稳定推导的语义增量。它应当有作用域、有证据、有状态，并能够随项目变化而维护。

### 5.2 项目协作

项目现在要完成什么、谁正在承担什么、工作之间如何依赖、成员作出了什么承诺、当前进展和阻塞是什么，以及工作如何被继续和交接。

### 5.3 项目治理

谁可以在什么范围内观察、建议、行动和决策，产出如何被验证，冲突如何处理，何时需要升级，以及人类如何保持对项目目标、价值边界和高风险事项的最终治理。

共享认知是协作的必要基础，但仅仅让所有 Agent“知道同样的事情”并不足以形成协作。项目协作空间还必须维护活跃的工作状态和公开的治理边界。

## 6. 系统目标

### 6.1 建立项目认知连续性

项目认知不应随着会话结束、Agent 更换、Leader 离开或团队解散而消失。后续成员应当能够站在项目已经形成的认知基础上继续工作，而不是反复从原始材料中考古。

### 6.2 降低成员进入项目的成本

经授权的新成员应能在无需人类重复补课的前提下，获得当前角色和任务所需的最小充分理解，并知道如何继续探索项目，而不是一次性加载全部项目资料。

### 6.3 提升项目行动的边界正确性

系统应帮助成员理解任务适用于什么、不适用于什么，产品语言如何对应项目行为和工程对象，哪些约束必须遵守，以及哪些地方证据不足、需要澄清。

首要收益是减少范围错判、错误类推、遗漏、重复踩坑和不必要行动，而不只是提升搜索速度。

### 6.4 支持多 Agent 的自主协作

Agent 不应只能等待某个 Leader 派发工作。项目可以允许成员在授权范围内发现、提出、认领、协商、委派和接续工作，也可以在适合的场景中采用集中调度。

系统不强制固定的组织拓扑，而是支持集中领导、横向协作、临时小组和自主认领等多种形式共存。

### 6.5 消除项目上下文的单点依赖

Leader 可以负责方向、优先级、跨领域取舍和必要仲裁，但不再负责独占、记忆和分发整个项目的上下文。

Leadership 是项目授予的一种可替换角色，而不是其他成员的上下文所有者或项目的父进程。

### 6.6 让项目随工作持续成长

需求、排查、实现、测试、评审和交接产生的有效认知，应在经过适当治理后回到项目，供未来成员继承。

系统要减少知识只存在于某个人、某个 Agent 或某段聊天记录中的情况，同时允许项目认知被修正、质疑、替代和淘汰。

### 6.7 保持人类对项目的治理

人类不再承担所有成员之间的信息中继和日常上下文补充，但仍负责项目目标、价值判断、权限边界、重大风险和不可逆决策的治理。

系统的目标不是移除人类责任，而是让人从重复补充上下文和微观调度，转向定义边界、处理关键分歧和监督项目如何形成决策。

## 7. 成员与角色

### 7.1 Agent 成员

Agent 是项目认知的消费者，也是项目工作和新认知的贡献者。Agent 可以来自不同模型、框架或提供方，并拥有独立生命周期。

系统不要求 Agent 进程永久运行。需要长期存在的是成员身份、角色、权限、承诺、工作状态和历史贡献；具体 Agent 实例可以结束、恢复或被替换。

### 7.2 人类成员与治理者

人类是项目空间中的一等参与者，而不只是系统外部的管理员。人类可以贡献和纠正项目认知、参与工作与决策，并对特定领域拥有最终治理权。

### 7.3 Leader

Leader 是项目中的协调和决策角色，可以确定优先级、处理责任空缺、组织工作、解决跨领域冲突并代表项目作出特定承诺。

Leader 可以更换，也可以按领域存在多个。Leader 的权力来自项目授予的职责，而不是因为其他 Agent 都由它创建。

## 8. 协作原则

### 8.1 项目优先于成员

成员围绕项目进入和离开，项目不围绕某个 Agent 的会话建立和消亡。

### 8.2 项目中心不等于无治理

本系统追求的是认知和协作不依赖单一 Agent，而不是所有成员对所有事项拥有相同权力。责任和决策权可以按角色、领域、风险和事项分布。

### 8.3 共享基线不等于强制共识

真实项目中允许存在不同视角、未验证判断、冲突信息和尚未解决的分歧。系统维护的是共享、可追溯的认知基线，而不是把所有成员压缩成单一叙事。

### 8.4 项目是协作中的隐含第三方

Agent 之间可以直接沟通，但具有项目影响的请求、承诺、结论、分歧、决策和交接不能只停留在成员私下交流中，而应以适当形式回到项目。

这是一种制度归属，不意味着所有消息都必须由中央系统转发。

### 8.5 最小充分认知优于完整灌输

所有成员共享同一个项目认知基础，但不意味着所有成员在任何时刻都接收完全相同的全部内容。系统应根据角色、任务、权限和当前状态提供足以行动的项目视角。

### 8.6 关键状态持续外化

项目连续性不能依赖成员退出前的一次总结。重要认知、行动意图、责任、进展、风险和决策应当在工作过程中持续成为项目可继承的状态。

## 9. 主要使用场景

### 9.1 加入项目

新的人类或 Agent 成员获得项目地图、当前局势、角色边界和相关工作，形成有效参与项目所需的情境意识。

### 9.2 接收或发现工作

成员可以接受指派，也可以根据角色、能力和权限发现、提出、认领或协商工作，并理解它与项目目标、其他工作和历史决策之间的关系。

### 9.3 跨角色与跨资产协作

产品、设计、研发、测试和运维等成员，可以围绕同一项目认知在多个产品端、仓库、文档和环境之间协作，而不需要各自重建一套互不相通的上下文。

### 9.4 决策与验证

成员能够识别自己可以自主决定的范围、需要其他角色参与的事项以及必须交给人类治理的问题。重要结论保留依据、适用边界和责任归属。

### 9.5 交接、退出与替换

成员退出或被替换时，未完成的责任、当前进展、关键判断、风险和未决问题仍留在项目中，使其他成员能够继续工作。

## 10. 非目标与边界

本项目不是：

- 普通文档搜索、向量检索或知识库产品；
- 只服务于单个代码仓库的代码助手；
- 替代代码、PRD、设计稿等原始事实来源的新事实源；
- 隐藏在系统内部、负责理解和调度一切的超级 Agent；
- 必须由单一 Leader 控制的固定 Agent Team；
- 彻底取消 Leader、角色差异或人类责任的无中心组织；
- 保存所有聊天、草稿和成员内部分析的全量记忆系统；
- 保证所有 Agent 拥有完全相同上下文或永远达成一致的机制；
- 要求 Agent 会话和运行实例永久存活的托管系统。

系统不替 Agent 完成具体专业工作，也不自动成为项目真理。它维护的是可共享的项目认知、协作状态与治理边界，并帮助成员在这些边界内共同工作。

## 11. 目标状态

当本项目达到目标时，应当出现以下状态：

- 新成员能够在很少依赖人类重复解释的情况下恢复到可工作的项目熟悉度；
- Agent 的更换、会话结束和团队结构变化不再导致项目认知和工作状态整体丢失；
- Leader 更换后，项目仍能恢复当前局势并继续运行；
- 多个 Agent 可以基于共同项目认知自主协作，同时保留清晰的角色、责任和决策边界；
- 项目中的关键判断、承诺和决策能够被追溯、质疑和修正；
- 未知、冲突和过期信息会被显式暴露，而不是被包装成虚假的一致答案；
- 每次工作都可能使项目更容易被下一位成员理解和继续，而不是制造更多只能依靠个人解释的隐性知识。

可以用一句话概括项目的长期愿景：

> 让不断变化的人类与 Agent 成员，在没有任何单一 Agent 承担项目记忆单点的前提下，建立足够一致且可追溯的工作认知，按照明确的角色和决策边界自主协作，并在加入、工作、交接和离开的全过程中维持项目连续性。

## 12. 项目空间宪章

在上述定位和目标之上，项目空间的状态归属、成员权责、Agent 自主、人类治理、规范写回与历史边界，已经进一步定义在独立文档中：

- [项目空间宪章](project-space-constitution.md)

项目定位与目标是系统设计的方向约束；项目空间宪章是 Human 与 Agent 共同协作时不能默默跨越的治理边界。具体对象关系、权限和能力状态继续以核心模型、领域规范和当前实现为准。
