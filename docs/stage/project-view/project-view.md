# 项目视图定义与项目上下文关系

> 本文只固化当前已经明确的概念与设计顺序，不定义数据结构、存储、同步、更新、检索、权限、接口或用户界面。

## 1. 文档目的

此前关于项目上下文的多版设计，主要围绕以下问题展开：

- 如何识别上下文内容；
- 如何维护和更新上下文；
- 如何检索并向成员交付上下文。

这些方向本身并非错误，但设计顺序过早进入了复杂的上下文关系。项目上下文需要以稳定、直接的项目对象和当前状态为坐标；在这些基础尚未明确之前设计上下文，容易让上下文同时承担项目状态、项目导航、当前直接状态的表达和关系解释。

因此，后续设计首先定义**项目视图**，再根据项目实际运行中暴露的信息缺口设计项目上下文。

本文回答两个问题：

1. 项目视图是什么，首先需要让人或 Agent 直接回答哪些一阶问题；
2. 项目视图与项目上下文分别表达什么，二者如何关联。

## 2. 核心定义

### 2.1 项目视图

项目视图是：

> 项目在当前时点的直接可见面，使人或 Agent 无需复杂推断，就能了解项目是什么、要做什么、进行到哪里、有哪些稳定责任位置，以及当前有哪些工作、需求、问题和资源。

项目视图表达项目已经明确登记或可以直接取得的当前状态。它首先提供项目的基本轮廓、对象和导航坐标，不负责解释对象之间尚未显式化的复杂原因、影响和延伸关系。

“视图”在本文中是概念与产品能力，不预先规定它是一份持久文档、一个数据库对象、一个聚合查询还是一个用户界面。

### 2.2 项目上下文

项目上下文是：

> 围绕项目整体或项目视图中的项目对象，在项目运行和实际工作中逐渐积累的语义增量，用于解释原因、特殊依赖、潜在影响、适用边界、注意事项和其他无法由直接状态稳定回答的问题。

项目上下文不是项目视图的副本，也不应重新维护另一份项目目标、工作、需求、Issue 或资源状态。它引用项目视图中的对象，并补充这些对象之间或其周围的复杂语义。

### 2.3 一阶信息与二阶语义

当前采用以下初步区分：

| 项目视图主要回答 | 项目上下文主要回答 |
|---|---|
| 是什么 | 为什么如此 |
| 有哪些 | 存在哪些特殊依赖 |
| 在哪里 | 应当如何理解 |
| 谁或什么处于何种直接状态 | 可能影响什么 |
| 当前明确计划做什么 | 有哪些适用边界、例外和注意事项 |

项目视图处理一阶信息；项目上下文处理建立在这些信息之上的二阶语义。

这个区分不是最终的数据分类规则。尤其是决定、约束、直接关系和责任信息应在视图中呈现到什么程度，仍需后续讨论。

## 3. 项目视图首先回答的一阶问题

当前已经明确，项目视图至少需要让人或 Agent 直接回答以下问题。

### 3.1 这是什么项目

- 项目的定位是什么；
- 项目为什么存在；
- 项目大致解决什么问题；
- 项目的基本范围是什么。

### 3.2 项目当前要达成什么

- 当前项目有哪些目标；
- 各目标分别希望得到什么结果；
- 当前明确的主要方向有哪些。

项目目标不同于具体 Work 的工作目标。一个项目可以同时登记多个并列目标，例如提升稳定性和提高运行速度。MVP 暂不解释目标之间的优先级、冲突、依赖或权衡关系。

### 3.3 项目当前有哪些 Role

- 项目当前有哪些稳定的语义职责；
- 每个 Role 为什么存在；
- 每个 Role 直接负责什么，责任边界在哪里；
- 每个 Role 当前是否仍然生效。

Role 是 Project 内稳定、可识别的责任位置，也是未来 Role Context 的坐标。Role
本体只定义责任位置，不表示由哪个 Human 或 Agent 承担，不表示权限，也不预先建立
与 Work 的责任关系。本文只定义 Role 在 Project View 中的基本语义；完整字段和
后续实现边界另行设计。

### 3.4 项目当前采用哪些规划，各规划处于哪个或哪些阶段

- 当前各份规划要如何推进项目；
- 各份规划具有怎样的明确逻辑和结构；
- 各份规划包含哪些阶段；
- 各份规划当前位于哪个或哪些阶段；
- 接下来已经明确计划推进什么。

阶段不是与规划并列的独立对象，而是规划内部用于表达分段、位置或推进状态的语义。Stage 是可以被稳定引用的 Project View 元素，但它的生命周期和规范位置从属于一个 Plan；稳定身份不要求它必须成为独立聚合或独立存储。规划不预设为单一线性序列，也可以具有并行、分支或其他结构。

一个项目可以同时存在多份规划。规划用于推进项目整体；首版中一份 Plan 可以关联零个或一个 Goal，一个 Goal 可以关联多份 Plan。不关联 Goal 的 Plan 仍然是 Project 的直接对象。首版不允许一份 Plan 同时跨多个 Goal，也不预设“唯一当前规划”。

项目视图只呈现已经明确的规划及其阶段，不负责推断未登记的隐含路线。

### 3.5 项目有哪些待办需求

- 当前有哪些已经提出的需求；
- 哪些需求尚未满足；
- 哪些需求已经进入工作，哪些仍在等待处理；
- 每个需求当前明确登记的处理优先等级是什么。

需求表达项目希望实现、改变或满足什么。

### 3.6 项目有哪些 Issue 需要解决

- 当前有哪些已知问题、缺陷、阻塞或待解决事项；
- 它们当前处于什么直接状态；
- 哪些已经解决，哪些仍然开放；
- 每个 Issue 当前明确登记的处理优先等级是什么。

Issue 表达项目已经发现了什么问题、缺口或异常。问题可以已经确认，但项目尚未决定或登记具体的解决工作。

需求和 Issue 都处于“项目有事情需要处理”的语义位置，但二者表达的来源和含义不同。本文保留这种概念区分，不预先决定它们是否共享数据结构或必须对应独立的数据对象。

### 3.7 项目当前有哪些工作

- 项目为处理哪些需求或 Issue 安排了工作；
- 每个需求或 Issue 当前有零个、一个还是多个相关工作；
- 哪些工作正在进行；
- 哪些工作处于其他直接状态，例如等待开始、暂停、已提交或已经结束；
- 每个工作当前明确登记的处理优先等级是什么。

工作是项目实际执行需求或 Issue 的单位。工作状态只表达执行状态；工作结束不自动表示对应需求已经满足、Issue 已经解决或所在阶段已经完成。

### 3.8 项目有哪些资源

- 项目关联哪些代码仓库、文档、设计、服务、环境和已有产物；
- 这些资源位于哪里；
- 可以从哪些入口继续了解或操作项目。

项目视图提供资源地图和稳定入口，不复制全部原始材料。

## 4. 项目视图中的对象关系

### 4.1 主要语言顺序

项目视图按照从项目意图到实际执行的顺序组织：

```text
项目
├── 目标（一个或多个）
│   └── 规划（零个或多个）
│       └── 阶段
│           └── 需求 / Issue
│               └── 工作
├── 未关联目标的规划（零个或多个）
│   └── 阶段
│       └── 需求 / Issue
│           └── 工作
├── 未规划的需求 / Issue（零个或多个）
│   └── 工作
├── Role（零个或多个）
└── 资源
```

所有对象最终都属于 Project。Plan 可以选择关联一个 Goal，也可以不关联 Goal；Requirement 和 Issue 可以选择进入一个 Stage，也可以保持未规划。这个顺序先回答“项目要达到什么”，再通过规划回答“当前阶段准备处理什么”，最后回答“为处理这些事项，实际安排了哪些工作”。Plan 与 Goal 的关联只表达首版中的直接组织关系，不自动表达 Goal 的达成条件。

### 4.2 当前概念语义

| 概念 | 当前理解 |
|---|---|
| 项目目标 | 项目当前希望达到的一个上层结果；同一项目可以有多个 |
| Role | 项目内稳定、可识别的责任位置，表达存在目的、直接职责、明确边界和当前是否生效 |
| 规划 | 项目为推进整体实现而形成的逻辑和结构 |
| 阶段 | 规划内部的分段、位置或推进语义 |
| 需求 | 项目希望实现、改变或满足的事项 |
| Issue | 项目已经发现、需要处理的问题、缺口或异常 |
| 工作 | 项目为处理需求或 Issue 而安排的实际执行单位 |

需求和 Issue 在结构上都表达“需要处理什么”，但保留不同语义；工作表达“实际执行什么”。

表中的呈现位置不预先决定数据对象边界。尤其是 Stage 当前确认属于 Plan 内部语义并具有稳定引用身份，但不据此要求它必须成为独立聚合或采用独立存储。

### 4.3 当前明确的直接关系

- MVP 中一个项目至少有一个目标，并且允许同时登记多个目标；
- 一个项目可以登记零个或多个 Role；Role 直接属于 Project；
- Role 本体不表示谁承担该 Role，也不与 Work、Plan 或 Executor 建立关系；
- 一个项目可以同时具有多个规划；一份 Plan 可以关联零个或一个 Goal，一个 Goal 可以关联多份 Plan；
- 规划包含并组织阶段；一个 Stage 必须且只能属于一个 Plan；
- 阶段把当前准备处理的需求和 Issue 纳入其处理范围；
- 需求和 Issue 首先属于项目；首版中可以尚未规划，也可以被放入零个或一个 Stage；
- Issue 可以通过独立的问题定位关系指向任意 Project View 元素；该关系不改变 Issue 的规划位置或所有权；
- 工作被安排去处理需求或 Issue；
- 一个需求或 Issue 可以尚未安排工作，也可以由一个或多个工作处理；
- MVP 中一个工作必须且只能处理一个需求或一个 Issue；
- 工作完成、需求满足、Issue 解决、阶段完成和规划完成是不同状态，不得隐式级联，也都不能自动推出任何项目目标已经达成；MVP 暂不建模 Goal 达成状态。

上述顺序是项目视图的主要阅读和组织方式，不预先规定底层必须采用严格树结构。一个工作同时处理多个需求或 Issue 不属于 MVP；如果真实使用证明单一归属不足，再重新讨论它应被拆成多个工作还是需要扩展关系。

上述对象关系、基数、未绑定对象呈现和 Issue 问题定位关系的完整首版设计见
[Project View 基本对象与关系设计](object-relation-design.md)。

### 4.4 直接结构关系与项目上下文

以下明确、登记且结构性的关系属于项目视图：

- 某份 Plan 当前关联哪个 Goal，或者尚未关联 Goal；
- 规划包含哪些阶段；
- 某个阶段准备处理哪些需求或 Issue；
- 某个工作用于处理哪个需求或 Issue；
- 某个 Issue 通过 `about` 关系指出哪个 Project View 元素上存在问题；
- 这些对象当前处于什么直接状态和明确登记的处理优先等级。

项目上下文补充这些直接关系无法稳定表达的复杂语义，例如为什么采用这种阶段顺序、为何把需求拆成多个工作、对象之间存在什么隐藏依赖，以及某项工作可能带来哪些后续影响。

因此，不能把“关系”整体归入项目上下文。项目视图表达明确结构关系，项目上下文表达原因、隐含依赖、潜在影响、例外和经验。

## 5. 项目视图与项目上下文的关系

### 5.1 项目视图是上下文的坐标系

项目视图为项目上下文提供优先坐标。上下文可以作用于项目整体，也可以关联目标、Role、阶段、规划、工作、需求、Issue 和资源等可识别对象。

```text
项目目标 ─┐
Role     ─┤
项目阶段 ─┤
规划     ─┤
工作     ─┼── 项目视图中的直接对象和状态
需求     ─┤
Issue    ─┤
资源     ─┘
           ↓
原因、依赖、影响、例外、经验和注意事项
           ↓
        项目上下文
```

没有项目视图提供这些坐标，上下文容易退化为缺少稳定归属的笔记、标签或摘要。

### 5.2 项目视图先于项目上下文

这里的“先于”首先是概念和设计顺序：

1. 先让项目的直接状态可见；
2. 让人和 Agent 使用这幅视图开展基础工作；
3. 观察仅凭项目视图仍然发生的误判、重复探索和信息缺口；
4. 再把无法由项目视图直接表达的关系、原因和影响沉淀为项目上下文；
5. 最后根据真实内容设计上下文的维护、更新、检索和交付方式。

这不要求项目视图一次性设计完成。上下文使用中发现的新需求可以反向推动项目视图演进，但不应以自由上下文记录替代明确的项目状态。

### 5.3 二者可以共同交付，但不能混淆归属

人或 Agent 最终获得的输入可以同时包含项目视图和相关项目上下文，但同一信息的规范归属必须清楚。

例如：

- 当前项目有哪些目标、各自是什么，由项目视图表达；
- 当前有哪些 Role、各自的目的和直接职责是什么，由项目视图表达；
- 项目上下文可以解释某项工作与其中某个目标之间的特殊关系；
- 后续 Role Context 可以解释某个 Role 的特殊依赖、例外和经验；
- 项目上下文不能复制其中某个目标并独立更新。

项目视图发生变化后，旧上下文不能继续代表当前直接状态。上下文如何更新或表达不再适用，留待后续设计。

### 5.4 项目运行会形成双向演进

项目视图为上下文提供附着点；项目上下文中的发现也可能产生新的明确项目对象。

```text
项目视图中的需求、工作或 Issue
        ↓ 实际工作
发现新的依赖、影响、风险或注意事项
        ↓
可能被识别并沉淀为项目上下文
        ↓ 必要时显式化
形成新的需求、工作或 Issue
        ↓
进入项目视图
```

新对象进入项目视图后，其存在和直接状态由项目视图表达；促成它出现的原因、影响链和经验仍可以由项目上下文表达。

## 6. 当前边界示例

以下信息适合首先由项目视图直接表达：

- 需求 R 已登记且尚未满足；
- 工作 W 正在进行；
- Issue I 当前开放；
- 仓库 A 是项目资源；
- Role A 当前生效，直接负责某一类项目职责；
- 项目当前处于 MVP 验证阶段。

以下信息更接近项目上下文：

- 工作 W 完成后可能影响需求 R2；
- Issue I 只会在某种特殊资源组合下出现；
- 某个术语在当前项目中容易引发特定误判；
- 某些资源之间存在不能从目录结构直接看出的特殊依赖；
- 某种处理方式曾反复导致后续问题，需要特别注意。

基础归属、显式状态和简单直接关系可以由项目视图表达；隐藏依赖、因果关系、潜在影响和经验性判断由项目上下文补充。二者的精确边界应通过后续真实使用继续确认，而不是现在建立完备分类体系。

## 7. 当前设计原则

1. **先直接，后复杂**：先让项目的明确状态可见，再处理复杂关系和语义。
2. **视图可以独立产生价值**：没有高级上下文能力时，人和 Agent 仍应能够从项目视图认识项目并开始基础工作。
3. **项目视图提供上下文坐标**：上下文可以作用于项目整体，也应尽量关联项目视图中的明确对象，避免成为无归属的自由文本。
4. **上下文不复制项目状态**：目标、工作、需求、Issue 和资源的当前状态仍由项目视图表达。
5. **从实际缺口生长上下文**：通过真实工作中的误判、重复探索和信息缺口识别需要沉淀的上下文。
6. **不过早追求完备分类**：当前不预先定义完整的上下文类型、关系网络和检索体系。

## 8. 概念层暂不定义

本文暂不决定：

- 项目视图由 Lora 持有、从外部系统聚合还是两者结合；
- 数据来源、权威性、版本、新鲜度和同步机制；
- Human 或 Agent 如何承担 Role，以及 assignment 的生命周期；
- Role 是否以及如何与 Work、Plan、Requirement 或 Issue 建立责任关系；
- Role 的权限、authority 与可执行能力；
- 决定和约束是否属于项目视图的最小必需内容；
- 各对象状态由谁、依据什么条件确认；
- 项目上下文的类型、生命周期、维护和更新方式；
- 项目上下文的检索、选择、预算和投影方式；
- 项目视图与项目上下文的权限和受限信息表达。

首版已经对基本对象关系、基数、Stage 表示和未规划事项作出设计选择。这些是为了形成可运行验证载体的首版限制，不把尚未验证的选择提升为永久概念定义。详见[Project View 基本对象与关系设计](object-relation-design.md)。具体后端字段、事件、CLI、存储、测试与 Buzz 接入方式见[Project View 后端实现设计](backend-implementation-design.md)。

## 9. 当前结论

当前阶段采用以下设计顺序：

> 先定义一幅简单、直接、能够独立使用的项目视图，让项目当前的目标、定位、Role、规划及其阶段、需求、Issue、工作和资源清晰可见；再以这幅视图为坐标系，从真实工作中识别并积累原因、依赖、影响、例外和注意事项等项目上下文。

项目视图表达项目当前现实的直接可见面；项目上下文表达建立在这幅视图之上的语义增量。
