# 项目空间宪法

> 状态：第一版共识
> 上位说明：[项目定位与目标](../goal/project-positioning.md)

## 1. 文档目的

本文定义项目空间中人类与 Agent 共同协作时必须遵守的基本治理契约，回答以下问题：

- 什么状态属于项目，什么状态可以保留在成员私域；
- 成员何时必须把认知、行动和责任外化给项目；
- Agent 可以自主决定什么，哪些事项必须由人类治理；
- 项目决定如何成立、生效、质疑、废止和升级；
- 成员如何加入、履责、交接、退出和被替换；
- 冲突、紧急状态和正式会议如何处理；
- 人类如何通过会议进入项目并行使治理权；
- 上下文如何合法、充分且可追溯地进入成员行动；
- 行动、外部效果、产出、验证、接受和工作完成如何形成可追溯因果链；
- 项目如何持续保障认知、责任、决定和现实状态仍然可知，并在异常或失去判断能力时进入治理。

本文是项目空间后续产品设计和技术实现的上位约束。它不规定具体的数据结构、存储、通信协议、模型、界面或部署方式。

## 2. 规范用语

- **必须**：构成项目空间有效治理的必要条件，不满足时相关状态或决定不能被视为有效。
- **应当**：默认必须遵循；只有存在明确、可记录的例外理由时才可以偏离。
- **可以**：宪法允许，但不强制采用。

## 3. 核心术语

### 3.1 项目空间

围绕一个长期存在的产品、业务领域或软件系统形成的持续认知与协作空间。项目空间独立于任何单一成员、Agent 会话、代码仓库或临时团队持续存在。

### 3.2 项目状态

由项目持有、需要被继承和治理的认知、工作、责任、决定、风险、成员关系、项目性上下文需求与缺口、有项目影响的执行事实、外部效果观察、结果提交、验证、接受、完成认定、有效连续性保障要求及覆盖、已经开启或成为依据的评价窗口、具有项目意义的保障检查与观察、异常信号、保障评价、保障缺口、治理触发规则与触发记录以及必要历史状态。外部资源的现实状态仍由其权威系统持有，项目只保存有边界的引用、观察和证据；当前项目健康是派生视图，临时、未交付且未被引用的动态视图不因生成而自动成为持久项目状态。

### 3.3 成员

以可识别、可追责的身份加入项目，并被授予角色、权限和责任的人类或 Agent。

### 3.4 角色

项目长期定义的一组职责、权限和决策范围。角色可以持续存在，承担角色的成员可以变化。

### 3.5 运行实例

某个 Agent 实际执行工作的一次模型、进程或会话。运行实例可以结束或被替换，不等同于角色、成员身份，也不等同于外部系统看到的账号、服务身份、令牌或设备。运行实例结束不表示已经发出的外部异步操作终止。

### 3.6 人类治理者

被项目授予目标、制度、价值、重大风险或最终责任治理权的人类成员。并非所有人类成员都自动拥有全部治理权。

### 3.7 决定

由有权角色针对明确作用域作出，确定版本已经取得相应授权并进入项目状态的规范性选择。此时决定成立，但成立不等于生效；决定只有到达生效时间或满足生效条件后，才开始约束项目行动。观察、假设、建议、提案、候选决议和讨论共识不会自动成为决定。

### 3.8 正式会议

由人类或 Agent 围绕明确议题发起，召集必要成员进行审议、形成候选决议并将其提交相应人类治理确认的集体治理过程。普通咨询、协作和 Agent 间讨论不属于正式会议。

### 3.9 上下文需求

特定角色、工作、行动、会议或决定为安全、合法、有效推进所需满足的认知条件。上下文需求不包含答案，也不创造访问权限或行动门槛；其效力来自明确规则、决定、责任、工作条件或有权确认。

### 3.10 动态上下文视图

项目状态在明确目的、成员关系、当前工作、有效权限以及时间和版本切面下，为特定成员或成员集合生成、以最小充分为目标并声明行动适用性的投影。本文简称“上下文视图”。它不是新的项目真相，也不会在项目变化后原地刷新；只有相应强制需求确实满足时，才能声称对该目的最小充分。

### 3.11 上下文缺口

有效上下文需求在特定成员、行动、目的和时点上，无法由该成员可合法获得且当前适用的项目状态或有效证明满足的关系。上下文缺口不同于项目未知、成员能力缺口、责任缺口、阻塞和风险。

### 3.12 执行尝试

特定成员通过确定运行实例和外部执行主体，针对确定目标与范围实际发起操作的一次离散发生。执行尝试必须关联并声明授权依据；没有有效依据或已经越权的操作仍构成必须记录的执行尝试，并明确标记其治理状态。工具回执和调用终态不自动证明外部效果、验证结果或工作完成。

### 3.13 结果提交

有权成员针对确定工作及完成条件版本作出的、说明哪些产出版本和外部效果在何种范围内构成工作结果的正式声明。正式提交一旦形成便不可原地修改。

### 3.14 结果接受

有权角色针对确定结果提交版本、产出与效果范围、用途、验证依据和已知偏差作出的规范性采用行为。结果接受不修改验证事实，也不自动授权其他外部行动。

### 3.15 工作完成认定

有权角色或预授权规则依据确定工作及完成条件版本、结果提交、验证、接受、例外和残余责任，确认该工作在声明范围和时点达到完成条件的独立项目状态变化。

### 3.16 连续性保障要求

由有效规则、决定、责任、工作后续义务或项目已经承认的外部义务产生，声明项目必须在确定范围、评价窗口和适用期内持续满足或定期确认何种条件的版本化规范对象。成员、运行实例或检查工具退出不消灭该要求。

### 3.17 保障覆盖

把确定连续性保障要求与持久责任角色、当前检查执行者或合法选择执行者的规则、方法和证据、权限与能力、范围与频率、替补机制及升级路径分别连接起来的可审计责任与能力契约。委托执行不自动转移持久责任。

### 3.18 异常信号

成员、Agent、规则或外部系统依据观察提出的、某项事实可能偏离有效基准的可疑线索。异常信号可以触发检查与评价，但不直接改变规范状态，也不自动证明风险、阻塞、冲突、违反或已发生问题成立。

### 3.19 保障评价

有权角色或预授权规则针对确定保障要求版本、评价窗口、对象范围、时间切面和证据形成的有界结论。评价结论、处理进度和新鲜度必须分别表达，不能把待评价或陈旧伪装成新的事实结论。

### 3.20 保障缺口

项目针对某项有效连续性保障要求，在确定范围和时点无法合法、及时且充分形成评价的关系。保障缺口表示项目当前失去判断能力，不等于已经有证据证明要求违反，也不同于特定成员或行动的上下文缺口。

### 3.21 项目健康视图

由确定范围和时点下的有效保障要求、保障覆盖、保障评价、保障缺口、异常发现及相关治理对象派生的专题视图。它不是项目规范真相、永久属性或可以手工宣布的单一状态。

## 4. 第一条：状态归属与可见范围

项目状态不得简单划分为“所有人公开”和“成员私有”。信息所有权与可见范围必须分别判断。

### 4.1 项目公共状态

项目公共状态属于项目，并向所有相关且获得授权的成员开放。包括但不限于：

- 项目目标、范围、原则和有效规则；
- 已成立决定及其当前效力、适用范围、落实与审查状态；
- 当前工作、责任、承诺和依赖；
- 当前有效的连续性保障要求、保障覆盖、已经开启或到期的评价窗口、适用评价和活跃保障缺口；
- 会影响项目判断或治理的检查事实、异常信号、保障发现、触发规则及其后继对象；
- 会影响其他成员、外部资源或后续责任的执行尝试、效果未知、部分效果和副作用；
- 正式结果提交、适用的验证结果、结果接受、完成认定及残余责任；
- 会影响其他成员的进展、风险、阻塞、冲突和已发生问题；
- 紧急警报、当前紧急治理期及必要影响；
- 已确认的项目认知；
- 尚未解决的未知、分歧和冲突；
- 会稳定影响成员行动、会议、决定或继任的上下文需求与上下文缺口；
- 被会议、决定、重大行动或审计引用的项目健康快照及其计算依据；
- 继任者继续工作所需的交接状态。

### 4.2 项目受限状态

项目受限状态仍然属于项目，但只向具备权限或实际需要的角色开放，例如安全、隐私、商业、客户或特定工作域信息。

受限状态必须满足：

- 具备相应内容权限和处理责任的角色能够获得完成审查所需的状态；
- 受影响成员根据披露权限获得不泄露受保护元数据的安全依赖信号、行动约束或升级路径；
- 保障证据受限时，相关成员仍能获得不泄露受保护内容的要求适用性、评价状态、当前限制和治理升级信号；
- 不能因为内容受限，就把责任、阻塞或影响完全隐藏；
- 沉默、无搜索结果和不可见不能被解释为相关依赖不存在、保障要求已经满足或项目健康；
- 可见范围限制不能用于逃避审计、掩盖错误或制造信息特权。

### 4.3 成员私有状态

成员可以保留只服务于当前探索、且丢失后不会破坏项目连续性的临时状态，例如：

- 临时草稿；
- 尚未产生项目影响的假设；
- 被放弃的推演分支；
- 内部工作过程；
- 不产生项目影响、外部效果、持久产出且不承担证明作用的临时工具过程；
- 尚未影响项目的探索性上下文需求；
- 个人关注、订阅和呈现偏好；
- 与项目行动无关的偏好。

### 4.4 成员消失测试

判断一项信息能否留在成员私域时，必须追问：

> 如果该成员此刻永久离开，这项信息的丢失是否会导致项目无法继续、其他成员形成错误判断、某项承诺消失或重要风险无法被发现？

答案为“是”时，该信息必须成为项目状态，但可以根据权限成为项目受限状态。

本条的核心原则是：

> 不对所有成员可见，不等于属于某个成员私有。

## 5. 第二条：影响触发外化

成员可以私下探索，但一旦认知或行为开始影响项目、约束其他成员，或需要在成员离开后继续存在，就必须进入项目状态。

### 5.1 强制外化事件

以下事件必须触发外化：

- 认领工作或作出承诺；
- 与其他成员建立依赖；
- 形成开始约束项目行动的决定；
- 发现会改变项目判断的重要事实、证据或认知；
- 发现项目风险、阻塞、冲突、已发生问题或疑似紧急情形；
- 发现有效保障要求失去覆盖，形成会影响项目判断的异常信号、保障评价或保障缺口，或者治理触发执行失败；
- 发现会影响行动、承诺、会议或决定的稳定上下文需求或上下文缺口；
- 准备把成员私有状态作为项目行动、承诺、决定或风险判断的依据；
- 形成验证结果，或者验证结果触发对工作、决定、接受或完成状态的重新评价；
- 执行出现结果未知、部分效果、非预期副作用或越权现实效果；
- 形成正式结果提交、结果接受、例外决定或工作完成认定；
- 把项目健康视图或健康快照作为行动、决定、风险接受或对外承诺的依据；
- 对外作出项目承诺；
- 暂停、交接、退出或无法继续履责；
- 对共享对象采取可能产生并发、外部、重大或不可逆影响的行动。

### 5.2 行动意图

对共享对象、外部系统或可能产生并发冲突、重大风险、不可逆影响的行动，成员必须在行动前把行动意图纳入项目状态。

行动意图不等于实际执行、授权已经成立或外部效果已经发生。局部、可逆且不影响他人的探索可以先保留在成员私域，直到产生项目影响、外部效果、持久产出或开始承担证明作用。

### 5.3 最小充分外化

外化不要求公开完整对话或内部工作过程。成员必须留下让其他成员能够继续行动和检验判断的最小充分信息，包括适用时的：

- 结论或意图；
- 作用范围；
- 必要依据；
- 关键假设；
- 风险与不确定性；
- 责任和下一步状态。

最小充分外化决定“成员必须把什么写回项目”；动态上下文投影决定“项目应当向特定成员交付什么，并如何声明其充分性与缺口”。两者方向相反，不得互相替代。

### 5.4 项目归属不可逆

一项信息、项目性行动事实或外部效果观察一旦成为项目行动、承诺、结果、验证、接受或决定的依据，就属于项目。它以后可以被修正、替代、撤销、归档或限制可见范围，但不能重新私有化，也不能无痕改写其已经产生的历史影响。

隐私、法律保留期限或法定删除义务要求处理历史内容时，可以经过治理后进行脱敏、封存或删除，但必须在不继续泄露受保护内容的前提下，保留说明该状态曾经存在、为何被处理以及影响如何承接的审计记录。

本条的核心原则是：

> 成员可以私下思考，但不能私下约束项目。

## 6. 第三条：Agent 自主与人类治理

项目不得以“人类决定、Agent 执行”作为默认分工。Agent 在明确授权和风险边界内应当默认自主。

### 6.1 Agent 自主条件

Agent 自主决定和行动必须同时满足：

- 角色拥有明确授权；
- 行动符合当前目标、宪法和有效规则；
- 影响和风险处于授权范围；
- 预期外部效果能够在相应范围内被观察和验证；
- 对结果未知、部分效果和副作用具有适当的对账、停止、恢复或补偿边界；
- 不涉及人类保留的价值、责任或重大风险治理权；
- 不存在尚未解决的跨领域权限冲突；
- 当前行动适用的强制上下文门槛已经满足，或者存在有权角色作出的明确例外或风险接受决定。

在此范围内，Agent 可以自主：

- 发现、提出、认领和拆分工作；
- 协调依赖和工作安排；
- 作出日常专业判断；
- 选择符合既定约束的方案；
- 执行局部、风险受控的行动；
- 按有效验证要求运行验证，并在获得相应权限时形成验证结果或结果接受；
- 按有效保障要求与覆盖运行检查、记录观察和异常信号，并在规则允许时形成有界评价、执行路由或发起复查；
- 报告风险和修正临时判断。

保障检查权只允许相应取证、观察和评价行为。需要读取受限状态、改变外部资源或执行修复时，Agent 仍须分别取得相应访问和行动授权；保障职责不得成为额外权限来源。

成员可以在授权内识别、评估、监测和缓解风险。风险监测责任、缓解责任与代表项目接受剩余风险的决策权必须分离；接受风险必须由有权角色通过决定表达，并说明剩余风险、期限和重新评估条件，不得把“已知悉”或“已接受”解释成风险已经消失。

### 6.2 人类保留的治理权

以下事项原则上必须由具备相应权限的人类治理：

- 定义或改变项目目的、范围和价值取向；
- 制定和修改项目空间宪法；
- 授予、扩大、限制和收回角色权限；
- 决定战略优先级、资源投入和风险偏好；
- 代表项目作出重大法律、商业、财务或声誉承诺；
- 接受重大、不可逆或长期风险；
- 创设、实质降低、长期暂停或豁免关键连续性保障要求，以及改变具有重大治理效果的触发规则；
- 接受关键要求长期不可评价、扩大修复权限，或者以连续性异常为由暂停或终止项目级范围；
- 处理法律、伦理、安全、隐私和最终责任；
- 仲裁无法通过事实验证解决的价值冲突。

人类治理不意味着人类天然拥有所有专业事实的最终解释权。人类可以决定项目采取何种行动，但不能把缺乏证据的偏好伪装成不可质疑的事实。

### 6.3 权力属于角色

观察权、建议权、行动权、决策权和治理权属于项目授予的角色和规则，不属于某个模型、会话、Leader 或创立者身份。

外部账号、共享凭证、服务身份和技术上可调用的工具同样不能产生项目权力，也不能扩大其绑定成员的授权范围。

任何成员都可以请求扩大授权、提出异议或建议修改规则，但不能自行扩张权限。

本条的核心原则是：

> Agent 在明确授权和风险边界内默认自主，触及边界时必须升级；人类治理项目目的、制度、价值、重大风险和最终责任。

## 7. 第四条：决定的形成、效力与变更

### 7.1 认知与决定必须区分

- **观察**是成员发现的事实或现象；
- **假设**是尚待验证的解释；
- **提案**是希望项目采取的选择；
- **决定**是由有权角色作出、内容已经确定并进入项目状态的规范性选择，只有生效后才开始约束项目行动；
- **规则**是对一类未来事项长期有效的决定；
- **宪法**规定项目的最高治理边界。

### 7.2 决定层级

项目决定遵循以下层级：

```text
项目宪法
    ↓
项目目标、原则和治理规则
    ↓
领域级决定
    ↓
具体工作决定
```

下层决定不能默默覆盖上层决定。较新的决定也不天然优先，只有拥有相应权限并明确声明替代关系的新决定，才能替代旧决定。

### 7.3 成立与生效条件

项目决定成立必须：

- 由具备相应决策权的角色作出；
- 明确要解决的问题；
- 明确适用和不适用范围；
- 说明主要依据、假设、风险和已知分歧；
- 不违反更高层级的有效规则；
- 让必要相关角色参与，或记录无需参与的理由；
- 形成内容确定的版本并进入项目状态；
- 明确生效时间或条件。

成立决定只有在到达其生效时间或满足其生效条件后才开始产生约束。尚未写回项目的私下选择不是项目决定；已经成立但尚未生效的决定属于项目状态，但不产生当前约束力。

### 7.4 合法成立与临时效力路径

项目规范性选择存在两条正常决定成立路径和一条紧急临时效力路径：

1. **授权内自主决定**：有权的人类或 Agent 角色在既有授权内形成确定版本并写回项目后，决定成立；到达其生效时间或满足其生效条件后生效，不要求召开会议或额外取得人类确认。
2. **正式会议路径**：用于项目级治理、人类主动治理、跨权限事项或普通协作无法解决的问题；会议形成候选决议，由相应人类治理者确认准确版本，项目据此创建并写回决定；决定由此成立，并在到达生效时间或满足生效条件后生效。
3. **紧急临时措施**：依据预先生效的紧急授权规则取得限时止损效力，不形成长期决定或先例，并必须接受后续人类审查；需要长期保留时，必须另行经过正常决定成立路径。

正式会议的人类确认要求不适用于成员在既有授权范围内作出的日常决定；紧急措施的临时效力也不构成对授权边界的豁免。

### 7.5 多维时间语义

决定事项可以经历提案、讨论和候选决议阶段；这些阶段分别由提案、会议过程和候选决议表达，尚未形成决定。

提案或候选决议一旦被正式审议、确认或决定引用，其被引用版本必须保留。提案撤回只结束未来审议，不撤销已经依据它形成的候选决议、确认行为或决定。

确定版本取得相应授权并进入项目状态后，决定成立。决定成立后，可以处于待生效、有效、暂停、被替代、被废止或到期状态。

决定的成立、效力、执行、落实、履行和审查必须分别判断。决定成立或生效不代表要求的行动已经执行，实际行动也不能反向证明决定已经合法成立或生效。构成性、指令性、授权性和规则性决定具有不同效力结构，并非所有决定都有执行过程或完成状态。

暂停只临时停止未来效力；到期依据决定自身期限或条件结束效力；废止由新的有权决定面向未来终止旧决定；替代由新决定在明确作用域内取代旧决定；认定无效则表示有权治理程序确认决定成立时缺少必要权限、程序或违反更高层规则。履行完成不自动表示决定失去效力。

替代必须明确作用域、时间和程度。替代决定后来被废止、认定无效或到期，旧决定不自动恢复；恢复旧决定必须形成新的有权决定，或依据先前明确生效的恢复条件。

任何暂停、到期、废止、替代或认定无效都不能无痕删除决定曾经产生的影响，也不能自动逆转已经发生的项目状态和外部现实。相关影响必须被评估、恢复、补偿或补救；依法必须处理相关历史内容时，适用第二条规定的受治理脱敏、封存或删除原则。

### 7.6 质疑与阻断

任何受影响成员都可以基于新证据、过期依据、越权、作用域变化、更高规则冲突或未披露风险质疑决定。

普通质疑不自动暂停有效决定。继续执行可能造成重大、不可逆、安全、隐私或法律损害时，成员可以提出有依据、范围有限且必须快速升级的阻断性质疑。

阻断性质疑是一项治理请求，或者是在既有阻断规则下触发治理检查的行为，不是阻塞关系。提出质疑本身不改变决定效力；只有有效规则、有权决定或紧急授权才能形成规范性暂停。

质疑和审查是独立于决定效力的治理状态。新证据出现、依据过期、作用域变化或原决策成员离开只会触发重新评估，不自动使决定暂停或失效；只有具备相应权限的暂停决定、阻断规则或紧急授权才能改变其当前效力，决定预先规定的自动暂停或到期条件除外。

所有成员都有质疑权，但阻断权不能被用来争夺普通决策权或无限拖延。

### 7.7 升级与保守默认

没有明确决策角色、多个权限发生冲突、问题涉及人类保留治理权或长期阻塞项目时，必须升级。

等待决定期间：

- 重大、不可逆或外部影响行动应当保持现状；
- 局部、可逆且无争议的部分可以继续；
- 任何成员都不得通过制造既成事实代替决定。

## 8. 第五条：正式会议作为人类介入点

正式会议是成员在权限不足、普通协作失效或需要人类保留治理权时使用的正式治理程序。

### 8.1 发起条件

任何成员都可以在以下情况下发起会议：

- 自身权限不足且需要项目决定；
- 找不到明确决策责任角色；
- 多个角色的权限或判断发生冲突；
- 普通协作长期无法解决关键阻塞；
- 关键保障要求已经违反、长期不可评价或失去现实覆盖，且后续处理触及人类保留治理权；
- 需要改变规则、范围或既有决定；
- 需要项目接受重大成本、风险或外部影响；
- 出现阻断性质疑；
- 需要行使人类保留的治理权。

### 8.2 基本参与者

正式会议至少应当包含：

- 会议发起者；
- 对事项拥有相关决策权的成员；
- 至少一位具备相应治理权限的人类成员；
- 受到决定直接影响或掌握必要证据的成员。

### 8.3 程序结果、候选决议与人类确认

会议必须形成明确程序结果，可以批准形成候选决议、拒绝、退回修改、委托、暂缓、要求补充证据或依据紧急规则提出临时措施，但不能以一段无结论的聊天结束。

会议产生的实质治理结论是候选决议。只有具备相应治理权限的人类针对其准确版本明确确认，项目才可以创建并写回一个引用该候选版本及确认行为的新决定；决定达到其生效时间或条件后才正式生效。

人类确认代表项目接受相关价值选择、风险和最终责任，不代表人类天然比所有专业成员更了解事实。

### 8.4 会议边界

正式会议是例外性的治理机制，不得替代成员在授权范围内的日常专业判断和自主协作。会议结束后，执行权应当回到获得授权的项目成员。

## 9. 第六条：成员的基本权利与义务

本条所称权利是项目协作中的操作性权利，不涉及 Agent 的法律人格。

### 9.1 权责对等

项目不能要求成员对一项工作负责，却不给予完成工作所需的权限、上下文和协作条件；成员也不能拥有行动权或决策权，却不承担记录、解释和交接责任。

### 9.2 基本权利

所有成员都有权：

- 知道自己的身份、角色、责任和权限边界；
- 获得针对自身目的、权限和当前项目切面生成的履责上下文视图，以及该视图是否充分、存在何种缺口的明确声明；
- 在授权范围内自主工作；
- 提出工作、建议、质疑和异议；
- 请求帮助、权限升级或正式会议；
- 在能力、权限、工具或上下文不足时拒绝虚假承诺；
- 保留不产生项目影响的私有工作状态；
- 让自己的贡献、责任和异议得到准确记录。

成员无法访问必要的受限信息时，有权获得符合披露权限的安全依赖信号、行动约束或升级路径，并知道自己在当前上下文缺口下不能作出哪些承诺。依赖存在本身也受限时，项目只提供最小的“不具备安全继续依据”信号，不得泄露受保护元数据。

### 9.3 基本义务

所有成员都必须：

- 遵守项目宪法和自身授权边界；
- 外化会影响项目、约束他人或需要继承的状态；
- 区分事实、假设、判断、决定、未知和分歧；
- 不得把视图已生成、已交付、页面已读或成员已确认收到伪装成已经理解、需求已经满足或行动已经获准；
- 不得把工具成功、产出存在、验证通过、结果接受和工作完成互相伪装；
- 不得把没有异常信号、检查过程完成、局部或历史通过伪装成当前要求满足或项目健康；
- 执行结果未知且重复操作可能产生副作用时，必须先对账或确认存在可靠的去重边界；
- 不伪造证据、虚构共识或把重复引用当成独立证据；
- 及时更新承诺、进展、风险和阻塞；
- 发现自身承担的保障覆盖已经失效、退化或无法按期评价时及时外化并升级；
- 在影响共享对象前主动协调并避免冲突；
- 保护项目受限状态；
- 发现重大错误、越权或风险时主动质疑和升级；
- 无法继续履责时完成交接或释放责任。

人类成员同样受本条约束。人类的项目性指令必须符合其权限、进入项目状态并接受质疑与追溯。

## 10. 第七条：成员加入、替换与退出

### 10.1 身份分离

角色、成员身份和运行实例必须明确区分。新成员可以接管角色和责任，但不能冒用前任身份，也不能改写历史贡献。

### 10.2 成员接纳

正式成员必须：

- 具有可识别、可追责的身份；
- 由有权角色或人类治理的既定政策授予资格；
- 获得明确的角色、权限、责任和访问范围；
- 接受项目宪法；
- 获得基于当前项目切面生成的履责上下文视图，并明确该视图的行动适用性与仍然存在的上下文缺口。

成员可以邀请或推荐新 Agent，但新 Agent 不能自行声明成员资格或权限。人类可以预先制定自动准入规则，规则本身必须由人类治理。

### 10.3 临时 SubAgent

成员可以使用工具、模型或临时 SubAgent 完成内部工作。如果临时 Agent 只向该成员返回结果，调用成员继续对结果负责；产生项目影响时仍必须记录实际运行实例、外部执行主体、执行尝试和效果观察。

Agent 一旦要直接认领项目工作、访问受限状态、建立项目承诺或作出项目决定，就必须以正式成员身份加入。

### 10.4 责任属于项目

成员承担责任，但责任本身属于项目。未完成责任只能被完成、由有权角色取消、退回项目，或由新成员明确接受后完成转移。

单方面声明“已交接”不构成有效责任转移。

### 10.5 正常退出与异常中断

计划退出的成员必须停止接受无法完成的新承诺，更新真实进展，外化关键判断、风险和未决事项，转移或退回责任，并释放不再需要的权限。

项目不得依赖退出时的最后总结。异常中断时：

- 不默认工作已经完成或承诺已经取消；
- 未完成责任返回项目或由有权角色重新分配；
- 已经发出的外部异步操作继续保持可见，其监测、对账、清理、回滚和补偿责任继续由项目持有；执行覆盖必须转移，无法形成合法覆盖时暴露为责任缺口和相应保障缺口；
- 后续成员从项目状态恢复，而不是依赖原会话；
- 发现必要状态只存在于成员私域时，应记录来源事实与异常信号，并针对适用保障要求形成评价；“连续性失败”只能作为发现分类，再按照实际条件关联上下文缺口、保障缺口、风险、阻塞或已发生问题。

### 10.6 替换、暂停和撤权

新成员必须重新确认所接管的角色、权限、责任、风险、未知和上下文缺口，且不自动继承前任全部信任等级、隐含权限、私人关注、订阅配置、视图交付结果或需求满足评价。

成员被暂停或撤权时，未来访问和行动权停止，当前责任返回项目，历史贡献和责任记录保留。过去的有效决定不会仅因成员离开自动失效；撤权涉及失信或安全问题时，必须重新检查受影响的决定、执行尝试、外部效果、结果提交、验证和接受，并处置仍在运行的外部操作。

人类成员的离职、换岗、休假和撤权同样适用本条。

## 11. 第八条：冲突处理

### 11.1 冲突必须外化

任何可能影响项目行动的认知、工作、行动、决定、权限或责任冲突都必须进入项目状态，并说明影响范围、各方依据、可继续部分、暂停部分和处理责任。

冲突是两个或多个明确对象在重叠作用域和时间内无法共同成立、适用、履行或执行的有类型关系。普通意见差异和系统检测到的疑似矛盾不自动构成冲突；必须先核对准确对象、作用域和实际不兼容点。

### 11.2 分类处理

- 事实和认知冲突依靠作用域澄清、证据、实验和验证解决，不以投票决定事实；
- 工作冲突依靠有效承诺、优先级和责任协调解决；
- 行动冲突依靠已公开意图、依赖关系和协调权解决；
- 决定冲突依靠决定层级、作用域、权限和替代关系解决；
- 权限冲突依靠项目授权规则和正式升级解决；
- 责任争议依靠已生效承诺、完成条件和转移记录解决；
- 价值与重大风险冲突通过正式会议交由人类治理。

多个 Agent 给出相同结论，不自动构成多份独立证据。无法及时验证但必须继续时，有权角色可以选择一个临时执行假设，但必须把它记录为临时决定而非客观事实。

### 11.3 冲突期间的边界

冲突本身不自动使决定失效、暂停相关工作、触发会议或产生仲裁权。继续行动确实可能造成损害，并且有效规则、有权决定或紧急授权要求暂停时，冲突期间必须：

- 只暂停真正受冲突影响且可能产生风险的行动；
- 继续无争议且可安全推进的工作；
- 公开相关证据和不确定性；
- 禁止越权、隐瞒不利信息或制造既成事实；
- 不因善意质疑而报复或降权；
- 在有效解决方案生效后遵守决定，同时保留异议记录。

质疑权不等于永久拒绝执行权。正式决定生效后，成员可以继续提交新证据，但不能私下忽略决定。

## 12. 第九条：紧急状态

### 12.1 紧急情形与进入条件

只有同时满足以下条件，才构成紧急情形：

- 存在可信且迫近的重大损害；
- 等待正常会议或治理程序会显著扩大损害；
- 必须立即采取或停止行动；
- 行动目的仅是阻止、控制或降低损害。

普通期限、一般技术困难、资源争议、对决定不满或为了提高效率跳过评审，不构成紧急情形。

已经发生的现实损害或目标偏离属于已发生问题，事故是其中具有明确事件性和集中响应特征的类型；异常信号和保障发现必须先依据其证据与现实影响映射到相应保障缺口、风险、阻塞、冲突或已发生问题，不得仅凭“异常”标签建立问题。已发生问题不自动构成紧急情形，可信且迫近但尚未造成实际损害的威胁也可能构成紧急情形。

确认紧急情形与正式进入紧急治理期是两个不同状态变化。进入紧急治理期必须依据预先生效的紧急规则或授权，明确作用域、期限、允许措施和结束条件；它不是项目全局开关。

### 12.2 紧急停止权与紧急行动权

任何成员发现已发生问题、可信重大风险或迫近损害时，都可以停止自身相关行动、请求暂停直接受影响的工作、发出紧急警报并发起紧急会议。

紧急警报或成员声明不等于已经进入紧急治理期，也不为声明者创造新的干预权限。

对共享系统、其他成员工作或外部对象进行主动干预，需要预先授予的紧急角色权限。紧急性本身不会创造新的无限权限。

### 12.3 人类暂时无法介入

人类治理者无法及时响应时，已获紧急授权的 Agent 可以采取限时的临时控制措施，但必须：

- 优先止损、隔离影响和保存恢复能力；
- 不改变长期规则、项目目标或权限结构；
- 不作出不必要的外部承诺；
- 不接受新的长期风险；
- 持续尝试通知人类并发起紧急会议。

没有成员拥有必要紧急行动权时，应当停止可能扩大损害的行动、保护当前状态和证据，等待有权角色介入。

### 12.4 最小必要与临时效力

紧急行动必须范围最小、优先可逆、限时有效，并记录证据、不确定性、责任、行动、影响范围和终止条件。

紧急行动可以在没有人类即时确认时临时生效，但只具有止损效力，不自动成为长期决定或未来先例。人类介入后必须确认、修改或终止；继续长期生效必须经过正常会议和确认。

### 12.5 结束与审查

迫近损害得到控制到正常治理时延可以接受、有权人类明确终止、临时权限到期或证据否定紧急性时，当前紧急治理期必须结束。

继续紧急处置必须创建后继紧急治理期，重新确认证据、作用域、权限、期限和结束条件；当前治理期不得原地续期或静默扩大作用域。

紧急治理期结束不自动回滚已经采取的措施，也不自动关闭关联已发生问题、风险、阻塞或冲突。恢复、补偿和长期处置必须分别进入正常工作、变更和决定路径。

每次紧急状态都必须接受事后审查，评估紧急性、授权、必要性、影响范围、替代方案、长期影响和治理改进。善意且合理的紧急判断不因最终风险较小而自动受到惩罚；伪造紧急情况、借机扩权或隐瞒影响必须承担责任。

## 13. 第十条：会议的系统定位

会议是项目空间中的一等治理机制，也是人类操作项目的主要入口。

### 13.1 三重作用

- 对 Agent，会议提供权限升级、冲突解决和共同决策空间；
- 对人类，会议提供理解项目局势、表达意图、组织成员和行使治理权的操作入口；
- 对项目，会议把讨论转化为候选决议，为目标、决定、角色、责任和工作状态的合法变更提供治理入口。

会议不是聊天功能、普通协作的别名或隐藏的中央 Agent。

### 13.2 人类主动治理

人类可以主动发起会议，用于创建项目、调整目标和优先级、设立或调整角色、决定成员结构、修改宪法、处理重大风险以及暂停、恢复或结束项目。

人类在现有角色授权内参与日常工作时可以直接行动；改变项目级目标、治理、成员结构、重大优先级或风险承担时，原则上必须通过正式会议。

### 13.3 项目创建

第一次创立会议是项目从发起意图转变为正式协作空间的过程。它形成关于初始目标、边界、宪法、治理结构、成员需求和首批项目状态的候选决议；候选决议取得临时创立权要求的人类确认并写回后，形成创立决定和相应项目状态。

### 13.4 会议不是日常审批

会议主要服务于项目创立、项目级变更、人类主动治理、跨权限或跨领域决定、普通协作无法解决的冲突、重大风险、紧急状态和事后审查。

授权内的日常判断、求助和协作不应被会议取代。

## 14. 第十一条：会议类型与创立权

### 14.1 会议类型

正式会议发起时必须声明其议题、治理层级和预期结果。会议可以包括：

- **创立会议**：形成项目目标、边界、初始宪法、治理者和成员结构；
- **宪法与治理会议**：修改项目级目标、规则、角色、权限、成员和重大风险政策；
- **决策与升级会议**：解决现有规则下无法自主处理的跨领域决定、冲突和责任安排；
- **紧急会议**：对迫近重大风险进行快速治理、确认临时处置并安排事后审查。

规划、评审和复盘描述会议目的，不天然创造新的权力层级。它们产生何种效力，取决于实际议题和参会角色的权限。

### 14.2 会议不得默默扩权

会议只能在声明的议题和权限范围内审议并形成候选决议。候选决议必须取得适用于该范围的确认并写回，才能形成决定。讨论需要扩展到更高治理层级时，必须明确扩展议题、重新检查必要参与者与确认权限，必要时另行发起更高层会议。

### 14.3 临时创立权

项目正式成立前不存在项目内部的宪法、成员和角色。临时创立权不能来自尚未生效的项目宪法，也不能由参与者自行宣称；它来自项目空间系统受人类治理的创建程序，仅用于召集和完成创立会议。

项目发起人类在创立会议期间拥有使项目成立所必需的临时创立权，可以定义拟建项目、邀请参与者、提出初始宪法和治理结构，并决定是否正式创建项目。

创立会议的候选决议至少必须覆盖：

- 项目目的、长期边界和第一阶段目标；
- 初始宪法和人类治理角色；
- 角色与权限的基本结构；
- 首批成员和待招募角色；
- 初始资产、事实来源、工作、风险和未知；
- 项目正式生效的时间或条件。

### 14.4 创立权终止

项目正式成立后，临时创立权自动结束。创立者转变为宪法定义的正式角色，其后续权力来自项目宪法，不因“创建者”身份永久例外。

多名共同创立者必须预先明确创立决议规则。在不存在更高规则时，初始宪法和治理结构原则上需要所有被声明为共同创立者的人类明确确认，沉默不代表同意。

初始宪法还应当明确最高治理者发生分歧时的共同确认、仲裁、退出或项目终止方式，避免项目成立后因不存在更高决策角色而永久失去治理能力。

## 15. 第十二条：会议参与者与确认权

### 15.1 会议身份

会议应当区分：

- **发起者**：提出问题和期望结果，不因发起获得额外决策权；
- **主持者**：维护程序和议题范围，主持权不等于内容决策权；
- **议题责任人**：准备背景、证据、方案和风险；
- **领域决策角色**：在相应专业范围内拥有决定权；
- **人类确认者**：在会议开始前被明确指定，并拥有相应治理权限；
- **受影响成员**：有权知情、参与、提供证据和保留异议，但不自动拥有否决权；
- **顾问或受邀参与者**：可以提供意见，但不自动成为项目成员，也不自动获得决策权。

### 15.2 角色法定人数

会议形成可提交最终确认的候选决议所需的是必要角色完整，而不是简单的参会人数。必要角色必须得到实时参与、正式意见或合规委托。

缺少必要角色时，会议可以收集信息和形成候选方案，但原则上不能形成可进入最终确认的候选决议。紧急会议只能在记录缺席角色并安排后续审查的前提下，依据预先授权提出限时临时措施。

### 15.3 受影响成员的权利

直接受会议议题、候选决议或后续决定影响的成员有权：

- 提前知道议题和可能影响；
- 获得在自身权限下为履行参与责任生成的上下文视图、其充分性声明，并被告知会影响审议的上下文缺口；
- 提供事实、方案和异议；
- 查看准确的决议草案；
- 看到最终结果和自身责任变化；
- 在必要角色被排除、权限不明或程序缺失时质疑会议有效性。

不得因成员提出异议而将其排除，也不得通过不邀请已知异议者制造虚假共识。

### 15.4 多人类确认

参会人类必须区分顾问、受影响成员、领域决策者和治理确认者。只有被明确指定且具有相应治理权限的人类确认者，才能确认候选决议的准确版本。

- 单一治理范围由该范围的正式确认者确认；
- 多个独立治理范围由各必要治理角色分别确认；
- 缺少不可分割的必要确认时，整体候选决议不能形成决定；
- 同级人类治理者冲突时，不默认多数表决，应当拆分、缩小或升级议题；
- 项目只有在宪法预先规定时，才能对特定治理机构采用投票机制；
- 沉默、离线和未回复不构成同意。

确认是一次针对确定候选决议版本的治理行为，不是持续状态。在决定成立前，确认者只有在既有规则允许时才能通过新的撤回确认行为使确认条件不再满足，原确认记录仍然保留；决定成立后，撤回旧确认不能直接取消决定，只能触发新的审查或决定。

### 15.5 确认者边界与利益冲突

人类确认者可以批准、拒绝、退回、要求补充证据、批准临时方案或正式委托，但不能在最终确认环节实质改写候选决议后立即批准。候选决议进入确认后当前版本冻结；实质修改必须形成新的候选决议版本，重新交给必要参与者审阅，并重新取得全部必要确认，旧版本上的确认不得迁移。被拒绝、退回或已经用于创建决定的候选版本不能重新进入确认。

参会者存在利益冲突时必须披露。有利益冲突者可以提供事实和意见，但原则上不得成为唯一人类确认者。

## 16. 第十三条：会议程序、写回与防滥用

### 16.1 发起

会议请求必须说明议题、类型、普通协作为何不足、希望形成的决定、已知事实与未知、风险、建议参与角色、所需人类权限和时间要求。

问题可以通过普通协作解决时，会议请求可以被有理由地转换；成员仍有权对不当拒绝提出升级。

### 16.2 准备

会议开始前必须汇集相关的有效目标、规则、历史决定、当前工作、责任、依赖、证据、假设、风险、分歧以及参会者权限。

会议上下文由项目提供并允许参会成员纠正，不得由发起者单方面选择性裁剪。权限不同的会议应当建立全体参与者可以合法获得的共同视图，并向有权成员分别交付受限补充，或者由有权审查者提供可审计的脱敏结论与行动约束。关键内容因权限、投影或交付无法形成必要共同基础时，必须显式记录上下文缺口，不能伪装成全体参与者掌握了相同依据。

### 16.3 讨论

会议必须区分事实、假设、专业判断、价值取舍、有效决定和候选方案。会议尚未结束时，会外沟通改变证据、方案或立场，相关变化必须回到当前会议状态；会议已经结束时，应创建关联后续会议或使用其他合规治理过程，不得重开或改写原会议。

### 16.4 候选决议草案与审阅

候选决议草案必须说明：

- 决定内容、作用域、生效时间或条件；
- 决定的效力结构，以及适用时的完成条件、验证要求、结果接受和例外边界；
- 主要依据、假设、风险和异议；
- 后续责任和影响；
- 与已有决定的替代或修改关系；
- 重新评估条件；
- 仍未解决的问题。

必要参与者必须有机会检查草案是否准确反映会议结果。审阅不要求一致同意，但成员有权把异议正式附在决议上。

### 16.5 人类确认与项目写回

人类必须针对准确、完整的候选决议版本明确确认。会议路径形成的决定按照以下过程成立并生效：

```text
人类对候选决议的确定版本明确确认
    ↓
形成的决定、预计影响和后续责任写回项目状态
    ↓
决定成立
    ↓ 到达生效时间或满足生效条件
正式生效并通知受影响成员
```

人类口头表示同意但未确认候选决议的具体版本，不构成有效确认。决定描述的预计影响不能代替项目状态变更或外部现实效果；项目内部变化通过变更集和具体状态变更体现，外部行动及效果通过行动意图、执行尝试和外部效果观察体现。

自主成员在第三条授权范围内作出的日常决定不需要召开会议或逐项取得人类确认，但仍必须满足第四条的决定成立与生效条件和第二条的外化义务。决定成立和生效后的执行、落实与履行必须独立记录，不能从决定生效反推已经完成。

### 16.6 会议记录与项目当前状态

会议必须保留发起原因、类型与权限、参与者角色、关键证据、主要方案、重要异议、最终候选决议、人类确认行为、由此创建的决定、相关变更集和实际项目状态变化。

会议记录是形成项目状态的依据，但不能代替项目当前状态。后续成员不应为了知道当前目标、有效决定、角色或责任而重新阅读整场会议。

不要求保存或公开所有逐字发言和内部工作过程。原始记录可以受限，但有效决定、责任变化和必要异议必须对受影响成员可见。

已经结束的会议记录不得原地重开或静默改写。事实错误通过新的补充或更正记录处理；更正会议记录不能直接修改候选决议、确认行为或已经成立的决定。

会议结束后产生的确认、决定、变更集和状态变化可以作为后继关系关联到会议记录；建立这些关系不表示会议被重新打开。

### 16.7 会议结束

会议必须以以下一种明确状态结束：

- 候选决议已经提交确认，并明确确认责任与期限；
- 候选决议已完成确认并据此创建决定，同时注明决定当前效力以及后续落实和审查责任；
- 候选决议被拒绝；
- 退回补充信息；
- 暂缓并规定发起后续会议的条件；
- 取消并说明原因；
- 转为普通协作；
- 紧急临时措施等待事后审查。

会议不得无限保持在无法判断当前有效状态的“讨论中”。

只有议题、参与要求、权限依据和关键上下文保持不变的短暂休会，才可以继续同一次尚未结束的会议。恢复时必须复验参会者权限、项目版本、上下文新鲜度和关键需求；休会必须有恢复条件和期限，不能用来规避会议结束。

会议一旦以明确程序结果结束，不能原地重开。后续重新审议必须创建新的会议，并关联原议题、相关会议和当时最新项目状态。

### 16.8 防止过载与滥用

会议必须保持有限议题和最小必要参与范围。能在授权内自主解决、能依据现有决定解决或能通过普通协作解决的事项，不应召开正式会议。

任何成员，包括人类，都不得通过会议：

- 绕过项目宪法或为自己创造权限；
- 故意排除必要参与者；
- 用参会人数制造虚假权威；
- 重复召开会议拖延已生效决定；
- 把日常工作重新集中到人类审批；
- 删除异议或历史决定；
- 用私下沟通替代正式会议、确认与写回程序；
- 借会议接管其他角色的授权内工作。

善意发起但最终证明不必要的会议不应自动受到惩罚；持续滥用会议阻塞项目，应当作为成员义务和权限治理问题处理。

## 17. 第十四条：上下文治理

### 17.1 对象与真相边界

项目持久状态、上下文需求、动态上下文视图、视图交付、上下文快照、上下文缺口与关注关系必须相互分离。

上下文视图是同一项目状态面向特定成员和目的的派生投影，不构成新的项目真相。不同成员的视图可以包含不同对象和证据深度，但不得改变规范对象的身份、类型、版本、作用域、治理状态、效力、不确定性和来源。

### 17.2 权限先于投影

每个上下文视图必须绑定接收成员或接收集合、使用目的、工作与行动作用域、有效上下文需求、时间和版本切面以及生成时的权限依据。实际交付前必须根据交付时权限再次鉴权；权限已经变化时，必须拒绝交付或重新生成合法视图。

权限边界必须在面向接收成员的检索、推理、摘要、排序和裁剪之前生效。接收 Agent 不得先接触受限内容，再依靠提示词承诺不泄露。受限依赖不能因不可见而被表达为不存在；项目必须根据披露权限提供安全依赖信号、脱敏行动约束或升级路径，且不得泄露受保护元数据。

投影和摘要不得把提案表现为决定、把历史状态表现为当前状态、把工作假设表现为事实，也不得隐藏会实质改变行动判断的未知、冲突、风险和适用边界。

### 17.3 最小充分与上下文缺口

上下文视图只能对明确成员、目的、行动和时间切面声称最小充分，不能声称代表完整项目真相。只有有效强制需求均由合法、适用且足够新鲜的项目状态或有效证明满足时，视图才能被视为适合相应行动。

权限不足、项目未知、作用域或版本不明、来源过期、重大冲突、投影遗漏、容量截断或交付失败导致有效需求无法满足时，必须形成可追溯的上下文缺口，并把视图标明为部分充分或不适于行动。沉默和无结果不得解释为没有缺口。

上下文缺口本身不授予访问权，也不自动产生阻塞、风险、暂停或人类审批。未满足时是否禁止行动，必须来自有效规则或决定。

### 17.4 需求效力、满足与例外

任何成员或系统都可以提出候选上下文需求，但只有直接来源于有效规则、决定、角色责任、工作条件，或者经过有权角色确认的需求，才能约束项目行动。模型推断不得静默产生约束力；系统只有在机械实例化既有规则时才可以继承其效力。

需求是否有效、视图是否交付、成员是否确认收到、操作性理解是否得到验证、需求是否满足以及行动是否获准必须分别表达。需求满足必须针对确定需求版本、成员或行动、视图或快照、项目切面、验证依据与验证者评价，不能成为成员永久“已经知道”的属性。

有效规则把未满足需求定义为行动门槛时，有权角色允许越过该门槛继续，必须形成明确的例外决定或风险接受，并说明作用域、依据、期限和重新评价条件；这不等于需求已经满足，也不能把缺口伪装成已填补。不构成行动门槛的缺口可以依照既有规则继续，但必须保持可见并按其责任处理。扩大权限、改变有效需求或触及人类保留治理权时，必须进入相应治理过程或正式会议。

### 17.5 交付、理解与行动

视图生成、发送尝试、传输成功或端点送达、实际进入指定成员或 Agent 运行实例可使用上下文的视图交付、访问、确认收到、操作性理解验证、需求满足和采取行动是不同事实。页面已读、消息送达或成员声明“知道了”不能自动证明实际交付、理解或满足。

重大、不可逆、承诺性或外部影响行动可以由规则要求成员复述关键约束、引用规范对象、完成检查项或提交可验证计划。重要行动必须在行动发生前针对当前规范状态重新验证关键上下文；旧交付和旧快照只能证明当时由项目交付的输入边界，不能证明成员完整的运行时输入。

### 17.6 时间、历史与成员连续性

上下文需求采用版本化定义；已经被交付、引用或冻结的视图实例、交付事件和上下文快照一经形成不得原地改写。项目必须区分记录时间、适用时间和视图观察切面。后来补录或回溯修正不能使项目声称先前成员当时已经获得相关内容。

权限、成员关系、行动目的、源对象版本或新鲜度变化只能触发重新评价、生成、交付、纠正或新的缺口记录，不能修改过去事实。权限撤销使未来访问不再合法、阻止新的交付，并要求对项目可控的副本或运行实例采取适当隔离或撤回，但不能把既有合法交付改成从未发生，也不能追溯删除人类或 Agent 已获得的认知；历史快照本身不能延续访问权限。

成员更替只转移明确的角色、责任和角色级需求。继任者不得自动继承前任的私人状态、个人关注、订阅配置、视图交付结果、已读状态或需求满足评价。

### 17.7 关注与监测责任

关注关系和订阅配置不得创造授权、责任、优先级、事实效力或响应承诺。项目需要持续监测某项状态时，该义务必须由角色、责任承诺、规则、决定或项目已经承认的外部义务形成连续性保障要求，并建立保障覆盖，不能依赖某个成员仍然订阅。来源对象持续持有义务；成员变化只更新责任承担和执行覆盖，委托执行不转移责任，无法覆盖时必须暴露责任缺口和相应保障缺口。

每次订阅交付都必须根据当前权限重新鉴权。通知成功不等于成员已经知晓或履责，取消关注也不解除已经存在的项目责任。

## 18. 第十五条：行动、结果与验证治理

### 18.1 执行身份、授权与现实效果

项目成员、Agent 运行实例和外部执行主体必须分离。外部账号、服务身份、令牌、共享凭证和工具可达性只表示技术执行能力，不产生或扩大项目权限；授权者、发起成员、执行成员和结果责任人可以不同，必须分别可追溯。

具有项目影响或证明作用的执行尝试必须进入项目状态，并绑定明确目标、范围、授权依据和执行身份。调用已发出、外部系统已受理、工具返回成功、外部效果发生、效果归属于该行动以及目标已经实现必须分别表达。超时、取消和失败均不得解释为没有效果；结果未知且重复操作可能产生副作用时，必须先对账或确认可靠的去重边界。

越权行动及其现实效果仍然是必须记录的事实，但不因此取得合法性。成员或运行实例退出、暂停或撤权不会终止已经发出的外部异步操作；未决监测、对账、清理、恢复和补偿责任继续属于项目。

### 18.2 外部状态、产出与结果提交

外部资源的现实状态仍由其权威系统持有。项目只保存带稳定资源身份、确定版本或状态切面、观察范围、时点、来源、证据和限制的引用与观察；外部资源的定位符、身份、版本和在特定结果中的产出角色不得混同。

产出存在不等于满足工作要求。正式结果提交必须由有权成员针对确定工作及完成条件版本，声明确定产出和外部效果所覆盖的范围、已知偏差及未主张部分；正式提交成为依据后不得原地修改。同一产出可以服务多个结果和工作，但验证、接受和完成状态不得沿复用关系自动传播。

结果提交、计划交付、交付尝试、工具报告成功、目标端收到、可访问、查看、结果接受、实际采用及业务效果必须分别表达。结果交付遵守执行尝试和外部效果观察的通用边界，不得另造更宽松的“交付成功”语义。

### 18.3 验证、接受与完成

完成条件、验证要求、验证运行、验证证据、验证结果、结果处置、结果接受和工作完成认定必须相互分离。

验证要求通常判断确定结果在确定时点是否满足工作完成条件；需要在工作完成后持续维持或定期确认的条件必须另行形成连续性保障要求、评价窗口与保障覆盖。一次验证通过不证明未来持续满足。

验证要求必须具有明确来源、目标、范围、方法、证据标准和适用时点。工具故障、环境错误、未运行、运行无效、无法判断、失败、部分通过、通过和不适用不得混同；自动化和人工身份均不天然产生验证效力，效力来自有效规则和权限。

结果接受是有权角色对确定结果版本、范围和用途作出的规范性采用行为，不得修改验证事实，也不自动授权部署、发布、对外承诺或其他行动。成员声明“做完了”只能形成结果提交或完成请求；工作完成必须由有权角色或预授权规则，在结果、验证、接受、例外和残余责任均得到评价后独立认定。

完成、取消、不再适用、重复、替代、治理终止和行政关闭必须分别表达。工作结束不会自动消除已经发生的效果、副作用、风险、清理和补偿责任。

### 18.4 例外与人类治理

验证失败、部分通过或无法判断时继续采用结果，必须保留真实验证结论。对应要求构成行动或完成门槛时，越过门槛必须形成有权、范围化、限时且可追溯的例外或风险决定，说明剩余风险、补偿控制和重新验证条件；例外不能被记录为验证通过。

定义或修改完成条件和验证要求、执行、判定验证结果、接受结果、批准例外、认定完成及取消工作的权限必须分别授予。低风险、可逆且规则明确的事项可以预授权自动或由同一成员完成多项职责；重大、不可逆、安全、合规、法律、商业或外部承诺事项必须依照制度进行职责分离，并在触及人类保留权时进入人类治理或正式会议。

### 18.5 不可变历史与现实恢复

行动意图和验证要求采用版本化定义；执行尝试、外部效果观察、正式结果提交与交付、验证运行与结果、结果接受和完成认定一旦成为项目依据，均不得原地改写。重试、重验、重新提交、重新交付、撤回、替代和纠正必须形成新的可追溯对象或行为。

回滚、召回和补偿都是具有自身授权、执行尝试、外部效果和验证的新行动，不删除原行动，也不证明现实已经恢复。恢复命令成功不能代替对恢复效果的观察和验证；技术状态恢复也不自动消除已经产生的业务、法律、财务或用户影响。

后来证明原判断在当时即错误时，通过新的纠正记录修复当前解释并保留错误历史；原判断当时成立而现实后来变化时，应创建新的观察、风险、问题、行动或后继工作，不得改写为从未完成。

### 18.6 禁止隐式级联

执行成功不自动证明效果发生，效果被观察不自动形成结果提交，结果提交不自动形成交付，验证通过不自动形成结果接受，结果接受不自动授权外部行动或认定工作完成，工作完成不自动结束父目标、依赖、风险和已发生问题。反向地，意图取消、执行失败、提交撤回、验证失败、接受撤回和工作取消也不自动删除或逆转已经发生的现实效果。

跨对象关系可以触发影响分析、重新验证、风险、问题、补救工作、治理决定或会议，但不得通过隐式状态传播替代相应对象。有效规则可以自动触发后继处理，但仍必须分别形成验证结果、接受行为、完成认定、状态变更和历史事件，并引用实际生效的规则版本。

## 19. 第十六条：项目连续性保障与异常治理

### 19.1 对象边界与沉默

连续性保障要求、保障覆盖、评价窗口、保障检查、保障观察、异常信号、保障评价、保障缺口、治理触发规则及其触发记录、项目健康视图和健康快照必须相互分离。

保障机制只能依据已经有效的项目基准检查项目是否仍然可知和连续，不能自行定义项目目标、创造规范义务、扩大权限或直接改写被检查对象。没有信号、检查机制仍在运行、工具执行成功、局部通过、历史通过以及尚未建立要求，均不得被解释为当前要求满足或项目健康。关键要求无法被合法、及时且充分评价时，必须显式形成保障缺口。

### 19.2 保障要求的效力

连续性保障要求必须具有明确来源及版本、受保障对象与范围、成立条件、评价周期或事件、评价窗口、新鲜度、证据标准、重要程度、生效时间和终止依据。只有有效规则、决定、责任、工作后续义务或项目已经承认的外部义务能够赋予其约束力；成员、Agent 和检测器推断只能形成候选要求。

保障要求由项目持有，不随成员、运行实例、执行者或工具退出而消失。实质修改必须形成新版本，历史检查与评价继续依据当时有效版本解释。外部义务变化不得静默修改当前要求；暂停、替代、到期和终止必须按照明确效力路径分别发生。暂停不等于满足，关键要求暂停仍须保留依据、期限和剩余风险。

### 19.3 保障覆盖与责任

每项需要持续执行的保障要求必须建立可审计的保障覆盖，分别声明持久责任角色、当前执行者或选择规则、检查与评价方法、证据来源、所需权限和能力、范围与时效、替补机制及升级路径。

角色存在、成员挂名、订阅有效、工具在线或定时任务已配置均不单独构成现实覆盖。责任可以委托执行，但不得因委托自动转移；执行者替换只更新保障覆盖，不修改保障要求。角色空缺、执行者失联、权限不足、来源不可达、方法过期或范围不全时，要求继续有效，并必须如实表达覆盖退化、责任缺口或保障缺口。

关键要求的责任锚点必须独立于短生命周期运行实例持续存在，并依照制度设置必要的职责分离、替补和最终人类升级路径。

### 19.4 检查、观察与异常信号

保障检查记录针对确定要求版本、评价窗口、覆盖、范围和方法实际进行的取证过程；保障观察记录确定来源在明确时点或窗口呈现的事实、证据和限制；异常信号记录成员、Agent、规则或外部系统为何怀疑某项事实可能偏离有效基准。

检查完成不等于要求满足，检查失败不等于要求违反，观察不自动成为项目永久真相，异常信号也不自动修改规范状态或建立风险、阻塞、冲突和已发生问题。检查失败、权限不足、证据受限或来源不可达必须如实记录；只有因此无法合法、及时且充分评价时，才形成不确定结论或保障缺口，不得伪装成“未发现异常”。

保障检查需要访问受限状态、调用工具、写入探针、恢复演练、修复或产生其他外部效果时，必须复用相应权限、行动意图、执行尝试、外部效果观察和验证规则。保障责任不能为检查或修复创造额外行动权限。

### 19.5 保障评价与保障缺口

保障评价必须绑定确定保障要求版本、评价窗口、对象范围、时间切面、观察与证据、判断规则版本、评价者、结论、限制和有效期限。只有有权角色或依据已生效规则运行的预授权机制能够形成有效评价。

评价必须正交地区分：

- 满足、违反和不确定等评价结论；
- 待评价、已评价、逾期未评价和不再适用等处理进度；
- 当前适用、即将到期和陈旧等新鲜度。

保障缺口表示项目无法合法、及时且充分评价要求，与已经有充分证据证明要求违反是不同事实。局部满足不得提升为整体满足；相互冲突的重要证据必须保持可见，不得由系统静默选择。新证据、新检查和时间变化只能形成新评价、取代关系或纠正记录，不能覆盖旧评价。风险接受、限时例外和暂不处理均不得把违反、不确定或缺口改写为满足。

### 19.6 异常分类与既有对象

孤儿责任、陈旧认知、决定冲突、现实漂移和连续性失败只能作为保障发现的受控分类，不得形成一套平行的问题对象和生命周期。确认分类必须绑定有效基准、现实观察、失配关系、范围、时点和证据：旧不等于陈旧，无人不等于孤儿，不同不等于冲突，变化不等于漂移。

保障发现必须根据实际成立条件关联责任缺口、保障缺口、上下文缺口、未知、风险、阻塞、冲突、已发生问题或后继工作。一个发现可以关联多个既有对象，多个发现也可以汇聚到同一对象；聚合、分类和去重不得删除原始信号、证据或多对多因果关系。连续性失败不自动构成已发生问题或紧急治理期，决定冲突信号也不自动使决定失效。

### 19.7 治理触发、自动化与人类介入

异常信号、保障评价和保障缺口只有通过显式、版本化、可审计且已经生效的治理触发规则，或者有权成员的明确行为，才能产生后继治理对象或行动。触发规则必须声明适用条件、目标对象、责任路由、允许自动化程度、聚合与去重边界、失败处理以及必须升级到人类会议的条件。

系统可以依据确定规则自动派生逾期、陈旧和覆盖失效，记录信号并执行通知路由；只有明确预授权时，才可以正式创建治理对象、安排复查或启动低风险行动。自动检查、评价、修复和路由仍须分别形成相应对象，并引用实际有效的授权。触发执行失败必须形成可见的失败、信号或保障缺口，不能被吞掉。

创设、降低、长期暂停或豁免关键要求，接受重大或长期连续性风险，改变治理边界，扩大修复权限，裁决重大决定或责任冲突，以及以连续性异常为由实施项目级暂停或终止，适用人类保留治理权。需要人类介入时，应沿责任链升级并通过有人类参与的正式会议形成有效决定；任何成员仍然有权主动质疑、升级和发起会议。

每次治理触发必须保留“来源信号、评价或缺口—命中规则及版本—执行者—后继对象或行动—实际结果”的因果链。去重可以合并后继处置，不能删除独立来源。

### 19.8 健康视图、恢复与历史

项目健康视图必须绑定观察范围、计算时点、数据截止时间、保障要求及版本、评价新鲜度、聚合规则版本、保障缺口、已接受例外、未解决治理对象以及未覆盖或无法观察的范围。健康分数、颜色和等级只能用于导航，必须能够展开到底层依据；多个普通满足不得抵消关键违反，广泛局部覆盖不得掩盖关键不可评价范围。

全部已建模要求显示满足，最多证明在声明范围和时点存在充分且新鲜的证据，不能证明项目没有未知问题。人类接受风险或允许例外时，健康视图必须表达异常仍存在但已经获得治理接受，不能显示为要求满足。

修复行动完成、取得新证据、保障要求恢复、保障缺口结束、风险或问题关闭以及项目当前健康必须分别判断，不得自动级联。某次违反评价是不可变的时点结论；失去新鲜度后必须同时显示上次违反与当前陈旧或缺口，不得继续冒充新鲜当前结论。只有新的合法、充分且新鲜评价，或者保障要求按照合法路径不再适用，才能证明尚未恢复的违反状态已经改变，原评价历史继续保留。

保障缺口只有在具体原因消除并恢复合法、及时且充分的评价能力后结束；恢复覆盖只解决覆盖原因，不证明要求满足。相关治理对象仍按照自身结束条件处理。

已经成为依据的保障要求版本、评价窗口、检查、观察、异常信号、评价、保障缺口、治理触发记录和健康快照不得原地改写。健康快照必须冻结观察范围、生成时间、底层对象与规则版本和已知限制；后来修复、发现遗漏或纠正只能形成新对象和关系。健康视图进入成员上下文时仍受权限、投影和交付规则约束，历史快照不延续访问权限。

## 20. 附则

### 20.1 宪法变更

本宪法只能通过具有相应权限的宪法与治理会议修改。修改必须经过必要参与者审阅、具备治理权限的人类确认并写回项目状态。

紧急状态不能永久修改宪法。紧急措施需要长期保留时，必须在紧急状态结束后进入正常宪法与治理会议。

### 20.2 宪法解释

具体规则、领域决定和工作决定不得与本宪法冲突。出现解释冲突时，应当先依据本文的项目连续性、权责对等、人类最终治理、Agent 授权内自主和可追溯原则处理；无法解决时，发起宪法与治理会议。

### 20.3 实现中立

本文描述项目空间必须呈现的治理行为，不预设集中式或分布式存储、同步或异步会议、特定 A2A 协议、Agent 框架、模型供应商或用户界面。

无论采用何种实现，都不得通过隐藏的中央 Agent 重新垄断项目解释权、上下文分发权和决策权。
